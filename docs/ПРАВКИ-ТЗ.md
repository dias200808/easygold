# Правки в ТЗ — противоречия и пробелы

Список того, что в `docs/ТЗ.md` нужно исправить до начала работ. Это не придирки: каждый пункт при реализации либо остановит разработку, либо приведёт к переписыванию.

Формат: **что не так → что сделать**.

---

## §4–5. Типы товаров и каталог

**1. `product_type` задан на уровне игры, но Steam в самом ТЗ отнесён и к типу C, и к типу D.**
→ Перенести тип на `products` (с наследованием значения игры по умолчанию) и определить в §5, чем именно торгуем по Steam — логином, кодами или обоими.

**2. §4 объявляет «три принципиально разных механики», а описывает четыре типа.**
→ Привести в порядок. Для Telegram выдача идёт по username/user_id — это ещё один вид идентификатора; нужна обобщённая схема идентификаторов, а не жёсткие A/B/C/D.

**3. Тип B описан требованиями, которых модель не выдерживает: одна маска `id_regex` и одна подсказка на игру, а полей два.**
→ Метаданные второго поля (label, regex, подсказка) + региональная привязка товара.

**4. Стартовый каталог опирается на две механики, работоспособность которых не подтверждена.**
→ Roblox: перепродажа гифт-карт запрещена условиями Roblox без договора с авторизованным дистрибьютором. Steam: официального пополнения по логину для третьих лиц у Valve не существует. Либо подтвердить каналы закупки с документами, либо сократить стартовый каталог.

## §6–7. Пользовательский путь

**5. §6.1/§22 требуют неактивную кнопку оплаты до подтверждения ника, §19 разрешает продолжить без проверки при таймауте 3 с.** Прямое противоречие.
→ Выбрать одно правило. Рекомендация: разрешить продолжение через режим «Повторите ID» + чекбокс о невозвратности + `orders.id_unverified`, критерий §22 переформулировать.

**6. Критерий «кнопка неактивна до подтверждения ника» не имеет исключений для типов C и D.** Для типа C идентификатора нет вовсе.
→ Добавить в §22 оговорку по типам; признак поддержки валидации перенести на связку поставщик+игра, а не на поставщика целиком.

**7. Подтверждение ника заявлено как основной путь, хотя доступно единицам позиций.**
→ Поменять акценты: «Повторите ID» — основной путь, подтверждение ника — включаемая опция.

**8. Гость, потерявший письмо, не имеет способа найти заказ.** Ссылка на `/order/{token}` есть только в письме.
→ Показывать и предлагать скопировать ссылку **до** перехода на оплату; страница восстановления по email + номеру заказа с лимитом попыток.

**9. Возврат с платёжной страницы и отказ оплаты не описаны вообще.** Это массовый сценарий.
→ Описать: `return_url`/`fail_url`, экран «оплата не прошла», кнопка «Оплатить снова» для неистёкшего заказа (несколько `payments` на один `order`).

**10. Доступ к заказу «по номеру» (§3) против неугадываемого токена (§6.2) — и самого номера в модели нет.**
→ Добавить `orders.order_number` и правило: доступ по номеру — только вместе с email и с лимитом попыток.

**11. Отзыв «невозможен без покупки», но гость его оставить не может** — `reviews.user_id` обязателен, а у гостя `user_id` нет.
→ Сделать `user_id` nullable либо разрешить отзыв по `public_token`; уникальность по `order_id`; только для `delivered`.

**12. Поле промокода на чекауте при том, что промокоды относятся ко 2 этапу.**
→ Скрыть за флагом, из обязательных полей §7.3 для этапа 1 убрать.

**13. Блок доверия на главной опирается на данные, которых в MVP нет** (количество заказов, средняя скорость, отзывы).
→ На MVP — статические аргументы; счётчики включать по накоплении данных.

**14. Бюджет «2 секунды на 3G» против двух аналитических счётчиков и агрегатов на главной.**
→ Записать численный бюджет (вес первого экрана, порог LCP); счётчики — только после загрузки страницы; ключевые конверсии отправлять серверно; показатели блока доверия читать из предрассчитанных агрегатов.

## §8. Модель данных

**15. `external_id`, на котором держится вся идемпотентность §10.3, в модели отсутствует.**
→ Добавить, и развести два идентификатора: платёжный (номер заказа + номер попытки, уникален на попытку) и поставщицкий (стабилен на заказ).

**16. `orders.payment_id` и `payments.order_id` — двусторонняя связь, которая ломается на второй попытке оплаты.**
→ Убрать `orders.payment_id`, оставить 1:N + частичный уникальный индекс «один успешный платёж на заказ» + `current_payment_id` для активной попытки.

**17. В `orders` нет `expires_at` и нет метки времени большинства статусов** — планировщик из §9 и сортировка очереди из §15.1 нереализуемы как описано.
→ Добавить `expires_at` и по метке времени на статус + `status_changed_at`. Все пороги (30 мин, 15 мин, 24 ч) — в настройки, не в код.

**18. Нет снимков цены, закупки, партнёрской ставки и поставщика в заказе.** Изменение цены товара задним числом искажает всю финансовую отчётность §15.5.
→ Добавить неизменяемые снимки `price`, `cost_price`, `product_name`, `supplier_id`, `partner_percent`, `tier`.

**19. `products.stock_quantity` дублирует остаток по `stock_codes`, а автоскрытие товара через `is_active` необратимо** — после пополнения склада товар останется выключенным.
→ `stock_codes` — единственный источник правды; видимость считать как `is_active AND (тип ≠ C OR остаток > 0)`, `is_active` автоматически не трогать.

**20. Проверка загружаемых кодов на дубликаты (§15.2) несовместима с их шифрованием (§16.4)** — по шифротексту дубли не ищутся.
→ Детерминированный HMAC-отпечаток кода с уникальным индексом, дедупликация по нему.

**21. Выданный код лежит в `orders.delivered_payload` открытым текстом,** хотя §16.4 требует шифрования складских кодов.
→ Распространить шифрование и правило «показ только по явному действию с записью в аудит» на `delivered_payload`.

**22. Бронь складского кода не имеет срока жизни и защиты от повторного использования.**
→ `reserved_at`, фоновое освобождение зависших броней, уникальность «один использованный код — один заказ».

**23. `supplier_requests.order_id` обязателен, а валидация игрового ID происходит до создания заказа.**
→ Сделать nullable, добавить тип запроса (validate/create/status/balance) и правило архивации массовых валидаций.

**24. Нет сущности возвратов** — статус `refunded` означает два разных события (баллы и живые деньги).
→ Таблица `refunds` (тип, сумма, причина, кем создан, кем подтверждён, id операции провайдера, статус) с уникальностью активного возврата на заказ.

**25. `points_transactions` не может выразить ни отложенное начисление, ни его аннулирование.**
→ Добавить `status`, `available_at`, `posted_at`, `reversal_of_id`, `idempotency_key` (unique). Записать правило: проводки — источник правды, `users.points_balance` — кэш в той же транзакции, ежедневная сверка с алертом.

**26. Личный промокод партнёра описан в двух местах:** `partners.promo_code` и `promo_codes.partner_id`.
→ Убрать `partners.promo_code`. Добавить `valid_from`, лимит на пользователя, область по товарам и таблицу применений со состояниями reserved/consumed/released с освобождением при истечении заказа (иначе брошенные корзины выжигают лимит партнёрского кода, а без резерва код применяется в 50 параллельных заказах).

**27. Второй уровень партнёрской сети (§13.4, «1% с оборота приведённых партнёров») не имеет ни поля, ни ограничения глубины.**
→ `partners.referred_by_partner_id` + явное «глубина строго один уровень».

**28. `users.role` одним значением противоречит иерархии ролей §3 и статусу заявки партнёра.**
→ Роль как набор прав либо отдельный флаг персонала; признак партнёрства читать только из `partners.status`; заявка `pending` прав не даёт.

**29. `saved_ids` не поддерживает тип D,** который есть в стартовом каталоге.
→ Добавить `account_login`, `verified_nickname`, уникальность по набору идентификаторов.

**30. Нет таблицы аудита,** хотя он требуется §15.4, §16.9, §17 и §22.
→ `audit_logs` (кто, действие, сущность, id, before, after, ip, user_agent, время); `order_events.actor` разбить на `actor_type` + `actor_user_id`.

**31. Нет таблицы настроек,** хотя «настраивается в админке» встречается по всему ТЗ.
→ Таблица настроек с историей изменений + справочник уровней партнёров; все пороги читать только оттуда.

**32. Нет таблицы фоновых задач и планировщика,** хотя §9 и §10.3 их требуют.
→ Таблица задач (тип, payload, `run_at`, попытки, статус, ключ дедупликации, dead-letter).

**33. Нет ключей идемпотентности на создание заказа и платежа и нет лимитов суммы.**
→ `idempotency_keys` + серверные min/max и суточный лимит.

**34. Нет фискальных чеков.** Полностью отсутствующий раздел, обязательный по закону РК.
→ `FiscalProvider` + таблица чеков + задача после `paid` + ссылка на чек в письме и в карточке; сбой не блокирует выдачу, но алертит.

## §9. Машина состояний

**35. Матрица переходов не покрывает то, что требуют другие разделы.** Нет `canceled`, нет `partially_delivered`, нет ветки поздней оплаты, нет `failed → processing` (повтор оператором) и `failed → delivered` (поставщик выдал позже), нет `delivered → refunded` при том, что §12 и §22 его требуют.
→ Переписать §9 как **полную таблицу** «из → в → кто вправе → условие» и сверить со всеми сценариями §10–§13. Матрица должна быть единственным источником правды и для кода, и для ограничения в БД.

**36. Правило «расхождение суммы → `failed`» вместе с правилом «`failed` дольше 15 минут → возврат полной суммы баллами» даёт возврат полной суммы за наш счёт при недоплате.**
→ Ограничить автовозврат заказами с подтверждённым успешным платежом и совпавшей суммой; расхождение суммы — отдельная ветка с ручным разбором.

**37. «Если оператор не вмешался» не определено, а машина состояний не даёт оператору вмешаться.**
→ Определить «вмешательство» технически: назначение оператора либо явная кнопка «отложить автовозврат» с записью в события.

**38. «Ручная очередь» и «взять в работу» не выражены ни статусом, ни полем.**
→ `assigned_operator_id`, `assigned_at`, `fulfillment_mode`; атомарный захват; watchdog брошенного `processing`.

**39. §11.2 п.5 отправляет заказ в `failed` после 3 попыток, а §19 и §22 это прямо запрещают** («при недоступности поставщика заказ уходит в ручную очередь, а не в failed»).
→ Разделить классы ошибок: терминальные (неверный ID, отказ по бизнес-причине) → `failed`; транспортные (таймаут, 5xx, нехватка баланса) → ручная очередь.

**40. Оплата после истечения 30 минут не имеет ветки обработки.**
→ Описать политику; плюс требование: перед переводом в `expired` опрашивать статус у провайдера — защита от потерянного вебхука.

## §10. Платежи

**41. Заявления §10.1 о Kaspi не подтверждаются публичными источниками.** Комиссия «от 1%» частично подтверждается (0,95% за оплату Kaspi Gold), но лимит 5 млн ₸, зачисление «в течение одного рабочего дня» и «подключается директором из приложения Kaspi Pay» для интернет-эквайринга — нет. Официальный путь: заявка на `kaspi.kz/webpay/partnership` и договор. Технический протокол выдаётся мерчанту после подписания и публично не документирован. Цифровые товары запрещены в Kaspi **Магазине** (это маркетплейс, не эквайринг).
→ Убрать неподтверждённые числа или пометить «требует подтверждения». Немедленно запросить техпротокол, тестовую среду и креды. До их получения — собственный тестовый провайдер.

**42. §10.3 «если заказ уже `paid` — вернуть 200 и ничего не делать» скрывает вторую реальную оплату.**
→ Идемпотентность строить на уникальном ключе события (`provider | external_id | provider_payment_id | status | amount`), а не на статусе заказа. Ветка «заказ оплачен другим платежом» создаёт запись о переплате и алерт.

**43. «Полное логирование вебхуков без исключений» невозможно в рамках `payments.raw_request`:** при неверной подписи или неизвестном `external_id` заказа нет, а значит нет и строки `payments`.
→ Отдельная таблица входящих вебхуков, не зависящая от наличия заказа; `payments.raw_*` оставить для исходящих вызовов.

**44. Вебхук поставщика упомянут в §9 (кто устанавливает `delivered`), но в §11 его не существует.**
→ Либо убрать из §9, либо описать входящие вебхуки поставщика по тем же правилам §10.3. Отдельно: проверенные поставщики либо не имеют вебхуков вовсе, либо сами требуют polling — `getOrderStatus` обязателен всегда.

## §11–12. Выдача и возвраты

**45. Интерфейс `Supplier` с позиционными аргументами не покрывает типы C и D,** которые есть в стартовом каталоге.
→ Единый объект идентификаторов; `getOrderStatus` по нашему внешнему id (если поставщик так не умеет — автоповтор после таймаута запрещён, только ручная очередь).

**46. Один `products.supplier_id` против трёх реализаций выдачи, обязательного фолбэка в ручную очередь и цели 99,5%.**
→ `suppliers.kind`, порог баланса, и список поставщиков на товар с приоритетом; правило переключения с сохранением снимка исходного поставщика в заказе.

**47. «Полная сумма» возврата не определена.**
→ Формула: возврат = уплаченные деньги + списанные баллы; скидка не возвращается. То же в оферте.

**48. «Баллы не выводятся» (§23) против «возврат живыми деньгами по требованию» (§12).**
→ Прописать точку невозврата: денежный возврат возможен до зачисления баллов; после — списание баллов в размере возврата и запрет отрицательного баланса.

**49. Возврат баллами гостю невозможен:** у гостя нет аккаунта и баланса, а гостевой сценарий — основной.
→ См. Q25 в `ВОПРОСЫ.md`.

**50. Оплата баллами объявлена (§7.4), но не выражена ни в чекауте, ни в модели, ни в машине состояний.**
→ `points_applied` в заказе, блок списания в §7.3, жёсткий порядок применения, минимальная денежная часть; либо явный запрет 100%-оплаты баллами (иначе нужна ветка перехода в `paid` без вебхука).

## §13. Партнёрская программа

**51. Экономика промокода не ограничена маржой:** скидка 5% + вознаграждение 10% + эквайринг + налог могут превысить валовую прибыль заказа.
→ Правило «суммарная нагрузка не выше заданной доли валовой прибыли» + признак «промокоды не применяются» и максимальный процент скидки на товаре.

**52. База начисления и момент обновления оборота не определены.**
→ Зафиксировать базу, правило «оборот растёт при начислении и падает при возврате», и что новая ставка не применяется ретроспективно (фактическая ставка хранится в заказе).

**53. Антифрод §13.3 не работает для основного сценария и противоречит §16.11.** Сверка `partners.user_id` и `orders.user_id` бессмысленна для гостя (у него нет `user_id`), а отпечаток устройства — это данные сверх «email, телефон, игровой ID». Плюс сверка по IP даёт массовые ложные совпадения из-за CGNAT у мобильных операторов.
→ Сверять по нормализованным email и телефону; `device_hash` либо добавить в политику, либо отказаться от правила; IP использовать только как флаг, не как блокировку.

## §16–17. Безопасность и логирование

**54. §16.11 «только email, телефон и игровой ID» противоречит остальному ТЗ** (ip и user_agent в `orders`, отпечаток устройства в §13.3, разрезы по источникам трафика в §15.5).
→ Переписать как явный перечень: что собираем, зачем, на какой срок, что маскируем через 12 месяцев. Отразить в политике.

**55. §17 «хранить логи 12 месяцев целиком» против §16.11.**
→ См. Q31 в `ВОПРОСЯХ`: тела целиком, маскирование секретов сразу, маскирование ПД через 12 месяцев, доступ к сырым логам — только админ и только с записью в аудит.

**56. Нет 2FA админки, нет ограничения доступа к админке, нет защиты от бота на чекауте, нет ротации секретов.**
→ Добавить в §16.

**57. Нет проверки восстановления из бэкапа как отдельного требования** — §16.10 упоминает «регулярную проверку», но непроверенный бэкап равен отсутствию бэкапа.
→ Записать как обязательный пункт чек-листа запуска с записанной процедурой.

## §19, §21–22. Нефункциональные требования, этапы, приёмка

**58. Критерии приёмки §22 требуют того, что §21 относит ко 2 и 3 этапам:** возврат баллами, партнёрская программа, все страницы на двух языках.
→ Разбить §22 по этапам. См. раздел 7 в `ПЛАН.md`.

**59. Валидация ID включена в MVP, а интеграция с API поставщиков — только в этап 3.** Валидация — это и есть вызов API поставщика.
→ Переформулировать: в MVP входит транспортный слой к поставщику в объёме валидации (если поставщик её даёт) либо режим «Повторите ID» без вызовов.
