# Техническое задание

## Сервис пополнения игровых валют для Казахстана

**Версия:** 1.0
**Назначение документа:** полная спецификация для разработки MVP.

---

## 1. Что мы строим

Онлайн-магазин цифровых игровых товаров для рынка Казахстана. Пользователь выбирает игру и номинал, вводит свой игровой идентификатор, оплачивает через Kaspi в тенге и получает валюту на аккаунт в течение нескольких минут.

**Ключевая ценность продукта — не низкая цена, а возможность заплатить.** Официальные магазины игр принимают российские платёжные методы, а покупка внутри приложения удорожается комиссией App Store и Google Play на 30%. Мы принимаем Kaspi в тенге в два тапа. Вся архитектура подчинена этому: путь от входа на сайт до оплаты должен быть максимально коротким.

**Мы не платёжный сервис.** Мы магазин. Пользовательский баланс существует только как бонусные баллы и средства возврата, не пополняется деньгами напрямую и не выводится обратно на карту. Это принципиальное ограничение: пополняемый деньгами кошелёк с возможностью вывода юридически является электронными деньгами, а их вправе выпускать только банки второго уровня.

### 1.1. Основные сценарии

1. Гость покупает донат без регистрации — базовый и самый частый сценарий.
2. Зарегистрированный пользователь покупает повторно с сохранёнными игровыми ID.
3. Партнёр регистрируется, получает промокод и зарабатывает баллы с приведённых заказов.
4. Оператор обрабатывает заказы с ручной выдачей и разбирает проблемные.

### 1.2. Языки

Русский — основной. Казахский — полная версия интерфейса и отдельные SEO-страницы. Переключатель языка в шапке, выбор сохраняется в cookie. Английский не нужен.

## 2. Термины

| Термин | Значение |
|---|---|
| Товар (product) | Конкретный номинал в конкретной игре: «Standoff 2 — 1000 голды» |
| Игра (game) | Категория верхнего уровня, объединяет товары |
| Игровой ID | Идентификатор аккаунта покупателя в игре |
| Заказ (order) | Единица покупки: один товар, один игровой ID, одна оплата |
| Выдача (fulfillment) | Процесс доставки товара на аккаунт покупателя |
| Поставщик (supplier) | Внешний сервис или ручной оператор, выполняющий выдачу |
| Баллы | Внутренняя бонусная единица. 1 балл = 1 ₸. Тратится только на покупки |
| Партнёр | Пользователь с промокодом, получающий баллы за приведённые заказы |

## 3. Роли

**Гость.** Просмотр каталога, оформление и оплата заказа, просмотр статуса заказа по ссылке из письма или по номеру заказа.

**Покупатель.** Всё, что гость, плюс: история заказов, сохранённые игровые ID, баланс баллов, реферальная ссылка.

**Партнёр.** Всё, что покупатель, плюс: личный промокод, статистика переходов и заказов, баланс заработанных баллов, уровень вознаграждения.

**Оператор.** Доступ в админку: очередь заказов, ручная выдача, отмена и возврат, переписка с клиентом.

**Администратор.** Всё, что оператор, плюс: управление каталогом и ценами, поставщики и их настройки, модерация партнёров, финансовые отчёты, настройки системы.

## 4. Типы товаров — критично для архитектуры

Существует три принципиально разных механики выдачи. Тип товара должен быть заложен в модель данных с первого дня, иначе систему придётся переписывать.

### Тип A. Выдача по одному игровому ID

Покупатель вводит один идентификатор. Примеры: Standoff 2 (Player ID), PUBG Mobile (Player ID), Arena Breakout, Free Fire.

Поля: `player_id` — строка, только цифры, длина зависит от игры.

### Тип B. Выдача по двум идентификаторам

Покупатель вводит два значения. Пример: Mobile Legends — User ID (8–9 цифр) и Zone ID (4 цифры, отображается в игре в скобках). Zone ID определяет региональный сервер, и товар должен покупаться под соответствующий регион.

Поля: `player_id`, `zone_id`. Оба обязательны, оба валидируются отдельно.

### Тип C. Выдача кодом со склада

Покупатель ничего не вводит и получает код активации, который применяет сам. Примеры: Roblox (gift card), Steam Wallet коды.

Для Roblox это единственный безопасный вариант: Robux нельзя зачислить по нику, а схемы с передачей логина или покупкой через геймпассы приводят к блокировке аккаунта покупателя.

Поля: отсутствуют. Требуется таблица складских кодов и контроль остатка.

### Тип D. Выдача по логину (отдельный подтип A)

Пример: Steam — пополнение кошелька по логину профиля. Пароль, почта и отключение Steam Guard **не требуются и не должны запрашиваться**.

Поля: `account_login` — строка.

**Требование:** сайт никогда, ни при каких условиях не запрашивает пароль от игрового аккаунта. Это в явном виде указано на каждой карточке товара.

## 6. Пользовательский сценарий покупки

Основной путь, от которого зависит конверсия. Целевая длина — не более четырёх экранов.

1. **Главная.** Пользователь видит плитки игр. Клик по игре.
2. **Страница игры.** Список номиналов с ценами. Выбор номинала.
3. **Оформление.** Ввод игрового ID, проверка ника, ввод email или телефона, поле промокода, чекбокс согласия с офертой.
4. **Оплата.** Переход на платёжную страницу Kaspi.
5. **Страница статуса.** Автообновление статуса, финальное подтверждение выдачи.

### 6.1. Проверка игрового ID — ключевой элемент

Самый важный экран сайта. Неправильно указанный ID является основной причиной отмен заказов, а валюта, ушедшая на чужой аккаунт, не возвращается никогда — это прямой убыток.

**Требования:**

- После ввода ID и потери фокуса поля система отправляет запрос на валидацию поставщику.
- При успехе показывается блок подтверждения: «Это ваш аккаунт? **Nickname123**» с кнопкой «Да, это я».
- Кнопка оплаты неактивна, пока ник не подтверждён.
- Если поставщик не предоставляет валидацию для этой игры — вместо проверки показывается второе поле «Повторите ID», значения сравниваются, плюс визуально выделенное предупреждение о невозвратности.
- Формат ID валидируется на клиенте по маске, специфичной для игры (только цифры, диапазон длины).
- Для типа B оба поля с подсказкой-скриншотом, где именно в игре найти User ID и Zone ID.

### 6.2. Страница статуса заказа

Доступна по уникальной ссылке вида `/order/{public_token}` без авторизации. Токен — случайная строка не менее 32 символов, не последовательный ID.

Отображает: номер заказа, товар, игровой ID, сумму, текущий статус, время создания, таймлайн событий. Опрос статуса каждые 5 секунд, пока заказ не финализирован.

Вкладки: мои заказы (список со статусами и повтором заказа в один клик), сохранённые игровые ID, баллы (баланс и история начислений и списаний), пригласить друга (реферальная ссылка и статистика).

Промокод и реферальная ссылка. Статистика: переходы, заказы, оборот, начислено баллов — за сегодня, за 7 дней, за 30 дней, за всё время. Текущий уровень вознаграждения и оборот до следующего уровня. Материалы: готовые тексты и баннеры. Правила программы.

### 7.6. Статические страницы

Оферта, политика конфиденциальности, правила площадки, контакты, FAQ, страница партнёрской программы с формой заявки.

## 9. Машина состояний заказа

Единственный источник правды о заказе. Любое изменение статуса пишется в `order_events`.

```
created ──► paid ──► processing ──► delivered
   │          │          │
   │          │          └──► failed ──► refunded
   │          │
   │          └──► refunded
   │
   └──► expired
```

| Статус | Значение | Кто устанавливает |
|---|---|---|
| `created` | Заказ оформлен, оплата не подтверждена | Система |
| `paid` | Получено подтверждение оплаты от банка | Вебхук платёжной системы |
| `processing` | Заказ передан поставщику или взят оператором | Система или оператор |
| `delivered` | Товар доставлен, подтверждено | Вебхук поставщика или оператор |
| `failed` | Выдача не удалась | Система или оператор |
| `refunded` | Средства возвращены на баллы | Система или оператор |
| `expired` | Оплата не поступила в течение 30 минут | Планировщик |

**Жёсткие правила:**

1. Переход в `processing` возможен **только** из `paid`. Никакие иные сигналы — редирект браузера, сообщение пользователя, ответ фронтенда — не являются подтверждением оплаты.
2. Обратные переходы запрещены. Ошибочно доставленный заказ закрывается вручную с комментарием, а не откатывается.
3. Заказ в статусе `failed` дольше 15 минут автоматически переходит в `refunded` с зачислением полной суммы на баллы покупателя, если оператор не вмешался.

## 10. Интеграция с платёжной системой

### 10.1. Основной провайдер — Kaspi Pay

Подключается директором ТОО из приложения Kaspi Pay. Комиссия от 1%, зачисление на счёт в течение одного рабочего дня, лимит одной транзакции до 5 млн ₸.

### 10.2. Резервный провайдер — Freedom Pay

Подключается позже, требует готового сайта с офертой, политикой конфиденциальности, логотипами платёжных систем и описанием товаров. Используется для приёма карт Visa и Mastercard у пользователей без Kaspi.

Архитектура должна быть провайдер-агностичной: интерфейс `PaymentProvider` с методами `createPayment(order)`, `handleWebhook(payload)`, `getStatus(paymentId)`. Добавление второго провайдера не должно затрагивать бизнес-логику заказов.

### 10.3. Обработка вебхуков — обязательные требования

**Идемпотентность.** Платёжная система может доставить один и тот же вебхук несколько раз. Без защиты это приведёт к повторному заказу у поставщика и выдаче товара дважды за свой счёт.

Реализация: у каждого заказа есть уникальный `external_id`, передаваемый в платёжную систему. При получении вебхука:

1. Найти заказ по `external_id`.
2. Если заказ уже в статусе `paid` или дальше — вернуть `200 OK` и **ничего не делать**.
3. Иначе — обработать в транзакции с блокировкой строки заказа (`SELECT ... FOR UPDATE`).

**Проверка подписи.** Каждый вебхук проверяется на подлинность по подписи или секрету провайдера. Неподписанный или неверно подписанный запрос отклоняется с `403` и логируется как инцидент.

**Проверка суммы.** Сумма в вебхуке сверяется с `final_price` заказа. Расхождение — заказ в `failed`, уведомление администратору.

**Быстрый ответ.** Вебхук отвечает `200 OK` немедленно, вся тяжёлая работа уходит в фоновую очередь. Провайдер не должен ждать ответа поставщика.

**Полное логирование.** Тело запроса и ответа пишутся в `payments.raw_request` и `raw_response` без исключений.

## 11. Интеграция с поставщиком

### 11.1. Абстракция

Интерфейс `Supplier` с методами:

- `validatePlayer(game, playerId, zoneId?) → { valid: bool, nickname?: string }`
- `createOrder(sku, playerId, zoneId?, externalId) → { supplierOrderId, status }`
- `getOrderStatus(supplierOrderId) → { status, payload? }`
- `getBalance() → { amount, currency }`

Реализации: `ApiSupplier` (внешний API), `ManualSupplier` (ручная выдача через админку), `StockSupplier` (выдача кодом со склада).

Один товар привязан к одному поставщику. Смена поставщика у товара не должна затрагивать историю заказов.

### 11.2. Обязательные правила

1. **Заказ у поставщика создаётся только после статуса `paid`.**
2. Каждый запрос к поставщику передаёт наш `external_id` для идемпотентности на его стороне.
3. Каждый запрос и ответ пишутся в `supplier_requests`. Это единственное доказательство в споре и с покупателем, и с поставщиком.
4. Таймаут запроса — 30 секунд. При таймауте заказ не считается проваленным автоматически: сначала опрашивается статус через `getOrderStatus`.
5. Повторные попытки: 3 раза с экспоненциальной паузой (10, 30, 90 секунд), затем `failed` и уведомление оператору.
6. Перед созданием заказа проверяется кэшированный баланс у поставщика. Если баланса недостаточно — заказ уходит в ручную очередь, а не проваливается.

### 11.3. Ручная выдача

На старте большинство позиций выдаётся вручную. Это отраслевая норма для игр вроде Standoff 2, где даже крупные площадки выдают силами оператора за 10–15 минут.

Сценарий: заказ переходит в `paid` → создаётся задача в очереди ручной выдачи → оператор получает уведомление в Telegram → оператор выполняет пополнение вне системы → нажимает «Выполнено» в админке → заказ переходит в `delivered`.

### 11.4. Выдача кодом со склада

Сценарий: заказ в `paid` → система берёт первый код со статусом `available`, переводит его в `reserved` в транзакции → записывает в `delivered_payload` → переводит код в `used` и заказ в `delivered`.

Требования: при остатке кодов ниже настраиваемого порога — уведомление администратору. При нулевом остатке товар автоматически скрывается из каталога. Коды хранятся в зашифрованном виде и отображаются в админке только по явному действию, с записью в аудит.

---

## 12. Возвраты

При `failed` средства возвращаются **на внутренний баланс баллов**, а не на карту.

Обоснование: оборотные средства остаются в бизнесе, покупатель почти всегда тратит их здесь же, а возврат на карту стоит комиссии и занимает дни. Так работают действующие площадки рынка.

Возврат живыми деньгами возможен только по явному требованию покупателя и выполняется оператором вручную, с фиксацией в аудите. Это условие прописывается в оферте.

## 13. Партнёрская программа

### 13.1. Регистрация

Форма: ссылка на канал, платформа (TikTok, Instagram, YouTube, Telegram, Twitch), заявленное число подписчиков или средний онлайн, подтверждение возраста.

**Возрастной порог — 16 лет минимум, рекомендуется 18.** Обоснование: полная дееспособность в Казахстане наступает в 18 лет, сделки лиц от 14 до 18 требуют согласия законных представителей, а сделки лиц младше 14 совершают за них представители. Дополнительно минимальный возраст регистрации в TikTok и YouTube — 13 лет.

Порог по аудитории: от 300 подписчиков или от 100 зрителей на трансляции. Планка намеренно низкая — программе нужен объём мелких партнёров.

Первые 100 заявок модерируются вручную: проверка живости канала, тематики и накрутки.

### 13.2. Механика вознаграждения

У каждого партнёра свой промокод. **Промокод обязан давать скидку покупателю** — иначе его никто не введёт и вся система не работает.

Базовая схема: покупателю 5% скидки, партнёру 5–10% от суммы заказа баллами.

Уровни по накопленному обороту (настраиваются в админке):

| Оборот, ₸ | Ставка партнёра |
|---|---|
| до 100 000 | 5% |
| 100 000 – 500 000 | 7% |
| свыше 500 000 | 10% |

**Вознаграждение начисляется баллами, а не деньгами.** Баллы тратятся только на покупки на сайте и не выводятся. Это устраняет необходимость в массовых выплатах физлицам, снимает комиссии на переводы и превращает партнёра в постоянного клиента.

Начисление происходит не в момент оплаты, а через 24 часа после перехода заказа в `delivered` — чтобы отменённые и возвращённые заказы не порождали начислений.

### 13.3. Антифрод партнёрской программы

- Запрет применения собственного промокода: сверка `partners.user_id` и `orders.user_id`, а также email и телефона.
- Флаг при совпадении IP или отпечатка устройства партнёра и покупателя.
- Лимит на количество заказов по промокоду нового партнёра в первые 30 дней.
- Автоматическая заморозка начислений при доле возвратов по промокоду выше 15%.
- Ручной просмотр всех партнёров с оборотом свыше настраиваемого порога.

### 13.4. Реферальная программа покупателей

Отдельно от партнёрской. Покупатель приводит друга по ссылке и получает фиксированный бонус баллами с его первых заказов. Партнёр дополнительно получает 1% с оборота приведённых им партнёров.

## 14. Уведомления

### 14.1. Telegram-бот для оператора

Основной канал управления в первые месяцы.

Уведомления: новый оплаченный заказ с ручной выдачей (номер, товар, игровой ID, сумма, кнопка «Взять в работу»); ошибка выдачи; сбой запроса к поставщику; баланс у поставщика ниже порога; остаток складских кодов ниже порога; расхождение суммы в вебхуке; заявка партнёра на модерацию.

Кнопки действий прямо в чате: взять в работу, отметить выполненным, отправить в возврат.

### 14.2. Уведомления покупателю

Email: подтверждение заказа со ссылкой на страницу статуса; выдача выполнена; для типа C — код активации; возврат на баллы.

На сайте: обновление статуса на странице заказа в реальном времени.

## 15. Админка

### 15.1. Очередь заказов

Основной рабочий экран оператора. Фильтры по статусу, игре, поставщику, дате. Сортировка по времени ожидания — самый долгий сверху.

Для каждого заказа: карточка с товаром, игровым ID (кнопка копирования в один клик), суммой, статусом, таймлайном событий, полным логом запросов к поставщику.

Действия: взять в работу, отметить выполненным, отметить проваленным с указанием причины, вернуть на баллы, добавить внутренний комментарий, скопировать данные для выдачи.

### 15.2. Каталог

CRUD игр и товаров. Массовое изменение цен: пересчёт по наценке от закупочной цены. Включение и выключение товаров. Загрузка складских кодов файлом с автоматической проверкой на дубликаты.

### 15.3. Поставщики

Список, ключи API, текущий баланс, статистика по успешности выдачи и среднему времени за 7 и 30 дней. Тестовый запрос валидации ID прямо из интерфейса.

### 15.4. Партнёры

Очередь модерации заявок с превью канала. Список партнёров с оборотом, уровнем, долей возвратов, флагами антифрода. Блокировка и ручная корректировка баллов с обязательным комментарием.

### 15.5. Финансы

Дашборд: оборот, количество заказов, средний чек, валовая наценка, комиссия эквайринга, начисления партнёрам, чистая прибыль — за день, неделю, месяц. Разрезы по играм и по источникам трафика.

Метрики продукта: конверсия из посещения в заказ, доля повторных покупателей, среднее время выдачи, доля неудачных выдач.

### 15.6. Отзывы

Модерация перед публикацией. Привязка к конкретному выполненному заказу — отзыв невозможен без покупки.

## 16. Безопасность

1. **Пароли от игровых аккаунтов не запрашиваются нигде и никогда.** На карточке товара размещается явное уведомление об этом.
2. HTTPS обязателен, HSTS включён.
3. Все секреты — ключи поставщиков, платёжных систем, токены бота — в переменных окружения, не в репозитории.
4. Ключи поставщиков и складские коды хранятся в базе в зашифрованном виде.
5. Rate limiting: на валидацию ID — 10 запросов в минуту с IP; на создание заказа — 5 в минуту; на вход — 5 попыток, затем задержка.
6. CSRF-защита на всех формах, изменяющих состояние.
7. Параметризованные запросы к базе, экранирование пользовательского ввода при выводе.
8. Роли и права проверяются на сервере, не только в интерфейсе.
9. Аудит-лог всех действий администраторов: кто, что, когда, с какими значениями до и после.
10. Резервное копирование базы ежедневно, хранение 30 дней, регулярная проверка восстановления.
11. Персональные данные — только email, телефон и игровой ID. Не собирать и не хранить ничего сверх необходимого.

## 17. Логирование

Обязательно логируются: все вебхуки платёжных систем полностью; все запросы и ответы поставщикам с длительностью; все переходы статусов заказов; все начисления и списания баллов; все действия администраторов; все ошибки с трассировкой стека.

Срок хранения — не менее 12 месяцев. Логи заказов должны быть доступны из карточки заказа в админке в один клик: при обращении покупателя «не пришло» это единственное доказательство.

## 18. SEO и локализация

Отдельная посадочная страница на каждую игру, с уникальным текстом, на русском и на казахском. URL вида `/ru/standoff-2` и `/kk/standoff-2`.

Обоснование приоритета казахской версии: 27% поисковых запросов в Казахстане выполняются на казахском, а выход в топ по казахоязычным запросам занимает 1–2 месяца против 6–12 на русском из-за низкой конкуренции.

Требования: серверный рендеринг всех публичных страниц; уникальные title и description на обоих языках; разметка Schema.org Product и Offer; hreflang между языковыми версиями; sitemap.xml с обеими версиями; скорость загрузки первого экрана до 2 секунд на мобильном интернете.

## 19. Нефункциональные требования

**Мобильность.** Проектирование начинается с мобильного экрана. 42% пользователей в Казахстане выходят в интернет исключительно со смартфона, а основной канал привлечения — TikTok, то есть весь трафик мобильный.

**Производительность.** Первый экран — до 2 секунд на 3G. Валидация ID — ответ до 3 секунд, при превышении показывается индикатор и возможность продолжить без проверки.

**Доступность.** Целевой аптайм 99,5%. При недоступности поставщика сайт продолжает принимать заказы, ставя их в ручную очередь.

**Масштаб на старте.** Расчёт на 100 заказов в сутки и 2 000 посетителей в сутки. Архитектура не должна требовать переписывания при десятикратном росте.

## 20. Рекомендуемый стек

Обоснование: минимум движущихся частей, один язык на фронтенде и бэкенде, дешёвый хостинг, хорошая совместимость с генерацией кода.

- **Фреймворк:** Next.js (App Router), TypeScript, серверный рендеринг публичных страниц.
- **База:** PostgreSQL. ORM — Prisma.
- **Очередь фоновых задач:** BullMQ на Redis, либо таблица задач в PostgreSQL с воркером — на старте достаточно второго.
- **Аутентификация:** сессии на сервере, вход по email и паролю, опционально magic link.
- **Хранение файлов:** S3-совместимое объектное хранилище для иконок и скриншотов.
- **Стилизация:** Tailwind CSS.
- **Развёртывание:** VPS с Docker Compose или Vercel в связке с управляемым PostgreSQL.
- **Мониторинг ошибок:** Sentry или аналог.
- **Аналитика:** Google Analytics 4 и Яндекс.Метрика с целями на шаги воронки.

## 21. Этапы разработки

### Этап 1 — MVP, до запуска

Каталог игр и товаров. Страница игры и карточка товара. Оформление заказа с валидацией ID. Интеграция с Kaspi Pay, включая вебхуки и идемпотентность. Машина состояний заказа. Ручная выдача через админку. Telegram-уведомления оператору. Страница статуса заказа. Оферта и статические страницы. Логирование. Мобильная вёрстка.

Всё остальное в MVP не входит.

### Этап 2 — первый месяц после запуска

Регистрация и личный кабинет. Сохранённые игровые ID и повтор заказа. Внутренние баллы и возвраты на них. Отзывы, привязанные к заказам. Партнёрская программа с промокодами и кабинетом. SEO-страницы на двух языках.

### Этап 3 — второй-третий месяц

Автоматическая выдача через API поставщиков. Складские коды для типов C и D. Реферальная программа. Freedom Pay как резервный провайдер. Финансовый дашборд. Антифрод-правила.

## 22. Критерии приёмки

**Оплата и выдача.**
Заказ невозможно перевести в `processing` без подтверждённого вебхука. Повторная доставка одного и того же вебхука не создаёт второго заказа у поставщика. Вебхук с суммой, отличной от суммы заказа, отклоняется и порождает уведомление. Вебхук без корректной подписи отклоняется с кодом 403.

**Валидация ID.**
Кнопка оплаты неактивна до подтверждения ника. Для типа B оба поля обязательны и валидируются раздельно. Ни на одном экране нет поля для пароля от игрового аккаунта.

**Отказоустойчивость.**
При недоступности поставщика заказ уходит в ручную очередь, а не в `failed`. Заказ в `failed` дольше 15 минут автоматически возвращается баллами. Все запросы к поставщику видны в карточке заказа.

**Партнёрская программа.**
Применение собственного промокода отклоняется. Начисление происходит не ранее чем через 24 часа после `delivered`. Возврат заказа аннулирует начисление.

**Прочее.**
Все публичные страницы существуют на русском и казахском. Первый экран загружается быстрее 2 секунд на мобильном соединении. Все действия администратора видны в аудит-логе.

## 23. Что сознательно не входит в проект

Пополняемый деньгами кошелёк с возможностью вывода — это электронные деньги, выпускать которые вправе только банки второго уровня. Баллы не пополняются деньгами и не выводятся.

Выплаты продавцам на карты физических лиц — в модели донат-сервиса продавец один, и это мы сами.

Маркетплейс с чужими продавцами и эскроу — отдельный продукт следующего этапа, но модель данных не должна ему препятствовать.

Мобильное приложение — сайт с мобильной вёрсткой закрывает задачу полностью на первый год.
